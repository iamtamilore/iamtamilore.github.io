Multi-Channel Short-Form Video Production Pipeline

12 min read

One pipeline builds every episode on three channels publishing at volume, and a gate refuses any episode that fails it.

Built by Taiwo Alabi. Production system, Dublin, Ireland · October to November 2026

68 videos public on YouTube across three channels on 24 November 2026, with 12 more scheduled, every one through eight build stages and two gates that can refuse the episode. A fourth channel, Whybit, runs the same pipeline on YouTube only and has one public short.

Three channels publish vertical short-form videos on a schedule, and every episode is assembled from source images, narration and captions by machine. The system exists because the work is repetitive at scale and because a failure in it is public: a wrong frame in a published video cannot be quietly re-shot, and the people who already watched it are not watching the correction.

The gates are the load-bearing part. They run inside the driver, they refuse the work, and the refusal is written to a record.

What this evidences: production engineering with a hard quality gate. The number that matters is not the video count, it is that a build that looked finished once was not, and the pipeline now refuses to build that shape of episode again.

1. The problem

Short vertical video is cheap to make badly. A pipeline that renders an episode from a pile of images will happily render an episode that is missing most of its shots, because the renderer takes what it is given and pads the gaps.

The specific failures this system was built to stop:

  • Manual work at the render stage. Choosing frames and assembling videos by hand does not scale to three channels on a schedule.
  • The same shot reused across channels. A repeated shot reads as a repeated episode, and the channels are watched by the same people.
  • The same closing promise spent twice. A channel that promises the same next episode twice trains its audience not to believe it.
  • An image that is sideways. Cameras and downloads are not always upright, and a rotated frame reaches the finished video unless something checks it.
  • A missing frame, silently. The most expensive failure of all, and the reason the gates exist. Section 5 is about that one.

None of these are visible in a finished episode unless somebody looks. That is the problem with a defect that only a careful viewer would catch: the pipeline has to be the thing that looks.

2. What the system does

The input is a brief: the channel, the subject, the narration script and the list of shots the episode needs. The output is a vertical video with burned-in captions, a narration track, a music bed and a call-to-action card, plus the records that show how it was made.

Inside that, four things happen:

  • Source. For each shot the pipeline fetches candidate stills. A shot is one planned visual moment, and a shot need is that shot with the instruction that describes it. Each need gets its own search queries, about 50 candidates per need.
  • Select. A vision model reads the instruction and the candidates and writes a verdict for each one. The model ranks, a person decides. The verdicts are written to disk per need.
  • Assemble. Every accepted still is cropped to the vertical master, 1080 by 1920, and the clip is cut to the narration rather than to a fixed grid. The result is burned-in captions that follow the spoken words, and the captions use the script's spelling.
  • Publish. The episode is scheduled, uploaded, and written to the posting ledger with its title, its video id and its date.

Each channel carries its own instructions: its own subject list, its own measured subject ratios, its own voice preset, and its own format rules. Forgotten Fronts is a hard cut on the narration. Super Zenpai is the same. The Anime Hive format is deliberately the opposite, a 3.00-second grid with a blur-whip transition and one red word, and it exists to be a counter-example rather than a channel.

3. The eight stages

The driver runs the stages in this order:

SOURCE -> PREFILTER -> ROTCHECK -> PREFILTER -> SELECT -> CROP -> VERIFY -> BUILD

Source. Pull candidate images for each shot that is still needed. The single most expensive mistake in the pipeline is giving every shot the same search words: the selector dedups globally, so needs with identical candidates see an empty pool and the episode gets whatever few stills exist, repeated.

Prefilter. Drop anything unusable before spending time on it. Resolution, aspect, duplicates and obvious mismatches go here, before the expensive stages run.

Rotcheck. Detect and fix images that are sideways. Correction has to happen before selection, never after, because a frame chosen on the wrong orientation is chosen for the wrong reason.

Prefilter, again. The step people delete because it looks redundant. It runs a second time on purpose, after rotation has been fixed, so a corrected-but-otherwise-bad frame does not reach selection unchecked.

Select. Rank the candidates and pick the best ones. The model scores them, the person chooses. A transport failure is recorded as a transport failure, not as a model fault, so a timeout does not empty a run silently.

Crop. Cut every chosen frame to the vertical master. The crop is what makes a sourced image usable, and a crop that trims a character out of frame produces a technically valid frame that is useless.

Verify. Look at every cropped frame at full size before building. Full resolution only, not contact-sheet thumbnails: a frame under 400 pixels wide cannot reliably identify a character, and that mistake has already happened once.

Build. Assemble the clips, cut to the narration, add the captions, and refuse to write a file that the gates would refuse anyway.

The order is a correctness property, not a preference. Prefilter running twice is the clearest example of it.

4. The gates

The frame gate

Runs twice inside the driver, not in a checklist.

  • Coverage, after selection. Every shot need in the brief must have a usable candidate in its own verdicts. A usable candidate means a complete, provenance-backed accept with every required field true.
  • Provenance, after the crop. Every cropped frame must come from its own need's accepted candidate, no two frames may share a source picture, and the frame count must cover the needs.

The shot gate

Deterministic, and it reads the rendered segments with ffprobe when the frame directory has already been cleaned. A shot duration greater than 3.5 seconds fails and exactly 3.5 seconds passes. Explicit call-to-action card shots are excluded. The gate does not call a model, does not publish, does not queue and does not upload anything.

The post-render gate

Five checks on the finished file. Four of them cost nothing at all: they read the media with ffprobe, ffmpeg and Python.

Check What it reads Cost
Audio No trailing silence over 3.5s before the call to action, total duration within 3.0s of the voice track plus the card, music bed present zero
Caption track Zero phonetic corruptions, subtitles reach the final sentence, no frame repeated in sequence zero
On-screen captions The caption band and the caption colours read from the pixels of the rendered file zero
Visual One vision model judges every shot for subject, beat and framing against the brief and the never list one model call
Frame loop No duplicate frame sequence loops the episode zero

If any one of the five fails, the episode is refused and the process exits non-zero, so a caller cannot read a failure as a pass. The driver runs the gate with a healing loop, so a repairable defect is repaired and re-gated instead of shipped.

The visual check is the only expensive one, and it is the only one that can be incomplete. A still cannot show motion, cut rhythm or framing, so the gate passes the clip itself to the model rather than a frame.

5. Why the gates exist

On 22 October 2026 the GOJO episode built and looked finished. It was not.

The selector wrote verdicts for only 3 of 16 needs. The crop step does not fail on a missing need, it prints NO VERDICTS or nothing usable, every candidate rejected and carries on. The build then had fewer frames than the episode had beats, and the builder rescaled or repeated to fill the gap. Three stills were spread across sixteen shots. Frame 06 was a wrong character.

Nothing in the pipeline noticed. A human looking at the frames noticed.

A missing frame is a silent defect, because it looks like a finished episode. That is why the gates live where they do:

  • The coverage check runs after selection, before the crop, while the work can still be stopped.
  • The provenance check runs after the crop, before the build, and it is the one that catches the reused-still signature directly.
  • The gate is in the driver. A gate that lives in a document is a warning, a gate that lives in the driver is a gate.

Three more rules came out of the same period and are enforced rather than advised:

  1. Five queries per need. Identical query lists put the same candidates in every folder, and the global dedup then leaves half the needs with nothing.
  2. Every never-list names its beat. A global "no Kanao" rule once rejected the very need whose line was about meeting Kanao. Constraints are per beat.
  3. Pixel review at full 1080 by 1920. Six frames passed at 640 pixels and failed at full resolution.

Counts are distinct public video ids read from each channel's own Shorts listing on 24 November 2026. A further 12 episodes were scheduled and not yet public. A fourth channel, Whybit, runs the same pipeline on YouTube only: one public short, four scheduled and private, and six ids the uploader removed.

One episode is documented in full on this site as a worked example of the gate: Forgotten Fronts EP_MUSASHI, 40.1 seconds, 19 frames, 15 claims verified against the source and 2 cut, shipped on 27 October 2026. It kept 65.3% of its viewers past the midpoint on its first day, with 876 first-day views. Retention is the format signal for a channel like this, and it is the number the pipeline is built to protect.

7. The publishing layer

Publishing is scheduled work, and scheduled work fails quietly. Two mechanisms cover that.

A registry and a ledger. 27 named scheduled jobs run under one registry, so every expected run has a known name. Each run writes one append-only record to a JSONL ledger, 10,378 records so far. A job that fired and failed therefore leaves different evidence from a job that never ran, which is the only way to tell those two apart after the fact.

Claims. Before any actor builds or publishes an episode, it takes a claim, a lease with an expiry. The cron job, the supervisor and an interactive session all take claims through the same control script, so the same episode is not built twice, and a crashed build releases its claim rather than blocking the channel forever.

The posting ledger itself is the record of what went out: one line per post with the title, the video id, the upload time and the schedule. It is not the source for the published counts in section 6, which are read from each channel's own Shorts listing, because a row in the ledger records what was scheduled while the listing records what is public. The two differ, and the difference is the point: the ledger is what the machine believes, the listing is what the platform shows.

8. The model gateway

Every model call in this system goes through one gateway, and that is a deliberate constraint rather than a convenience.

The gateway chooses the model and the service for a job, applies a spend ceiling before the call goes out, serves a cached answer when the same request has already been made, retries one known transport failure, quarantines a response that burned reasoning tokens and returned no content, and writes one record per call with the job, the model, the token counts and the cost where the provider returned it.

Measured on the ledger on 24 November 2026:

Measure Value
Calls recorded since 9 October 2026 53,346
Media jobs recorded 988, of which 942 succeeded and 46 failed
Uploads recorded 58

That is what makes the rest of the system auditable. A stage that ran a model can be read back after the fact: which model, which prompt, how many tokens, what it cost, and whether the answer was accepted or quarantined.

9. Honest limitations

  • The published count is not an audience measure. 68 is what the channel listings show as public. It is not a view count, and apart from the first Forgotten Fronts episode this report does not carry per-episode audience numbers.
  • The gates have thresholds, not a published pass rate. The shot bound, the duration tolerance and the coverage rule are explicit and fileable, but the evidence does not carry a measured pass rate for the gates as a whole.
  • The visual check can come back incomplete. It is one model call on a clip. The OCR pass is advisory, because its measured hit rates are weak, and the caption styling check is deterministic but narrow.
  • The ledger counts attempts, not completions. 46 of 988 media jobs failed, and the failed ones are recorded as failures rather than silently dropped, which is the point, but the completion rate is not a claim about quality.
  • The channel plans are hand-maintained. The subject lists, the subject ratios and the voice presets per channel are curated. The pipeline does not discover a new subject, and for the Anime Hive format there is no subject catalogue at all, which the format plan says out loud.
  • This is verified by inspection and by its own records. The claims here come from the pipeline's code, the posting ledger, the model ledger and the publishing state. No independent party has audited them.

10. Reproduce it

The driver runs one episode, one stage at a time, and refuses to run a stage by hand:

python3 scripts/anime_hive/run_episode.py \
  --brief <episode>/brief.json \
  --channel <channel> \
  --root <sourced-root> \
  --ep <episode-dir> \
  --out <episode-dir>/episode.mp4 \
  --from source

The gates can be run on their own, against an episode that already exists:

python3 scripts/anime_hive/gate_frames.py --root <sourced-root> \
  --brief <episode>/brief.json --stage coverage
python3 scripts/anime_hive/gate_frames.py --root <sourced-root> \
  --brief <episode>/brief.json --stage provenance --ep <episode-dir>
python3 scripts/zenpai/watch_gate.py <episode-dir> --brief <episode>/brief.json

The publishing state, the claims and the per-channel counts come from one read-only command:

python3 scripts/pipeline/state.py
python3 scripts/pipeline/control.py claims

What cannot be reproduced from the repository alone is the media generation itself, which needs provider keys and credits, and the upload, which needs the signed-in channel accounts.

11. Terms used in this report

  • Beat. One line of the narration, with its planned visual moment.
  • Shot need. A beat that still needs an image, with the instruction that describes it.
  • Frame. One still image from a video, in this report a still chosen for a shot.
  • Verdict. The record a model writes about a candidate image: accept or reject, with the fields that justify it.
  • Brief. The file that carries the channel, the script and the shot needs for one episode.
  • Episode. One finished video and its supporting files.
  • Gate. A check that can approve or refuse an episode.
  • Ledger. An append-only record, one line per event.
  • Claim. A lease an actor takes before it builds or publishes, so the same work is not done twice.
