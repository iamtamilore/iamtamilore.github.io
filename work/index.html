Multi-channel short-form video production pipeline

The problem this system addresses

Creating short vertical videos for several YouTube channels can become repetitive and inconsistent when people must manually choose images and render every episode. This system prevents manual render-stage work, repeated shots across channels, repeated closing promises, and incorrect image rotation from reaching the finished video.

What the system does

This system turns source images into finished vertical short-form videos. A pipeline is a series of automated steps that pass work from one stage to the next. A vision model is an image-reading program that chooses a suitable frame using the written episode instructions, and ffmpeg is a command-line tool that assembles images, sound, timing, and video into a final file. Each channel has separate instructions, voice settings, and image supply rules so the channels can remain distinct.

How it works

  1. First, the SOURCE stage gathers possible images for each required shot. A shot is one planned visual moment in a video. Each shot need has its own search questions so different moments do not accidentally receive the same image candidates.
  2. Next, PREFILTER removes or rejects unsuitable source images before selection. This reduces the chance that the selection step spends time considering obviously unusable images.
  3. ROTCHECK corrects or checks image rotation before an image is selected. This order matters because selecting an image before fixing its orientation could cause the wrong version to be chosen.
  4. SELECT gives the written brief and candidate images to qwen3-vl-235b. A model is a trained computer program, and this vision model can inspect images and compare them with the brief. It chooses one frame for each shot need.
  5. CROP converts the selected image into the vertical 9:16 shape required for the short video. VERIFY runs quality checks, called QA gates, before rendering. A QA gate is a rule that must pass before work can continue.
  6. BUILD uses ffmpeg to create the final video. The fixed order is enforced by the main runner script, and the order matters because rendering before checks would allow known problems into the output.

Cron orchestration layer with append-only verification ledger

The problem this system addresses

Some scheduled jobs were failing without making it clear whether they had run and failed or had never run at all. This system prevents that specific loss of evidence by recording a separate result for each expected job run.

What the system does

A cron job is a task that a computer starts at a planned time, and each of the 18 jobs first passes through a small script that gives the run a known name. An orchestrator is a program that checks whether the expected jobs are running, and a registry is a list of those expected jobs. A ledger is a record that only adds new entries, so this system writes one JSONL record, meaning one JSON object per line, for each observed job outcome. The system can repair a drifted copy of one document, sends a notification only when the overall condition changes, and returns exit code 0 when healthy or 1 when not healthy.

How it works

  1. First, every scheduled job is routed through the common runner script with the job name as its first argument. This gives later checks one consistent name for identifying the job.
  2. Next, the runner records whether that named job actually started and what happened during the run. This matters because a failed run must leave different evidence from a run that never started.
  3. The orchestrator then compares the registry, which lists the jobs that should exist, with the append-only ledger, which records what actually happened. Comparing the expected list with the recorded outcomes exposes both missing runs and failed runs.
  4. For each check, the system adds a new per-run result instead of overwriting an older result. Keeping old entries makes the history reviewable and prevents a later status from hiding an earlier failure.
  5. If the document mirror has drifted, the orchestrator repairs that one known repairable problem. It does not claim to repair every possible job failure.
  6. The system compares the current health state with the previous health state before sending a notification. This order prevents repeated messages about the same unchanged problem.
  7. Finally, it returns 0 for a healthy check and 1 for an unhealthy check. This lets another program or service detect the result without reading the detailed ledger.

Posting quality gates A to E

The problem this system addresses

Several publishing channels could accidentally release posts with repeated subjects, reused closing promises, copied descriptions, weak results, or the wrong speaking style. This system prevents those specific mistakes from reaching a channel when the relevant checks are actually run.

What the system does

This system is a set of five named checks, called gates, that inspect a proposed post before publishing. A gate is a rule that can approve or refuse an item. The checks compare performance data, subjects, closing promises, affiliate text, channel voice, and speaking speed against required rules. Four gates are connected to the publishing workflow, while the fifth is defined but not actually enforced in the tested loop.

How it works

  1. Gate A checks the known ratio for the brief. A ratio is a measured result compared with a required baseline. If the ratio is below 1.0, the brief is refused because it does not meet the minimum performance rule.
  2. Gate B checks whether the subject has already been used and whether the closing promise has already been spent. A closing promise is the final invitation or expected next action in a post. Refusing repeats protects the publishing schedule from reusing the same idea or ending.
  3. Gate C follows the chain of available closing promises and ranks tied choices by lift. Lift means the measured improvement or response associated with an option. This gate is used to choose among acceptable options rather than simply accepting every option.
  4. Gate D creates the affiliate description when the required information is available. If the description cannot be created, it records the precise reason the affiliate check failed instead of silently allowing the item through.
  5. Gate E checks the channel's assigned expressive voice preset and its words-per-second pacing band. A voice preset is a stored set of speaking-style choices, and words per second measures how quickly narration is spoken. The documented loop for this gate has no assertion body, so it does not currently enforce the check there.
  6. The publishing scripts call Gates A and B during queue creation and call Gate D for affiliate descriptions. The source description does not show a publishing-path call for Gate C or an executed per-channel loop for Gate E.

Multi-model LLM gateway with budget, cache and spend ceiling

The problem this system addresses

Different tasks used to contact language models directly, so repeated requests could spend money again and there was no single record of what happened. This system prevents uncontrolled spending, missing records, incorrect routing, and accepting a response that used reasoning effort but returned no usable answer.

What the system does

This system is a central program that sends every language model request through one controlled route. A language model is software that reads messages and produces text, while an endpoint is the network service that receives the request. The system chooses a model and service, can use a saved answer instead of making the request again, checks spending limits, records the result, and can retry one known temporary provider failure. It also keeps provider information separate from user-maintained routing decisions so an automatic catalogue update does not replace a deliberate local choice.

How it works

  1. First, a caller sends a request to the gateway instead of contacting a model service directly. This order matters because the gateway can apply the same checks and record keeping to every request.
  2. Next, the gateway identifies the requested job, such as research or drafting, and resolves it to a primary model and possibly a fallback model. A primary model is the first model tried, and a fallback is a replacement used when the first route cannot complete the job. This keeps routing decisions in one place.
  3. If the caller supplied a specific model, the gateway uses that model's own provider and endpoint rather than looking it up as if it belonged to another provider. This prevents a valid model override from being sent to the wrong service.
  4. Before contacting a provider, the gateway creates a SHA-256 cache key from the model, messages, and request settings. SHA-256 is a repeatable method for turning those inputs into a fixed fingerprint. If the fingerprint already has an answer, the gateway returns the saved answer, which prevents an identical request from spending money twice.
  5. If there is no cached answer, the gateway estimates the request cost and compares it with the per-call budget. It refuses the request when the estimate is above the allowed amount, before provider usage occurs.
  6. The gateway then reads the day's previous costs from its ledger and checks the daily cumulative cap. A ledger is a local record of events, and a cumulative cap is a maximum total for the day. This check comes after the per-call check because both the individual request and the day's total must be safe.
  7. The gateway sends an approved request to the selected endpoint. For the specified kie.ai Claude route, it retries a temporary provider error with a bounded backoff, meaning it waits for a limited amount of time between a limited number of attempts. This handles a temporary failure without retrying forever.
  8. When a response arrives, the gateway checks for a reasoning burn. This is a response where the completion token count equals the reasoning token count and the visible content is empty. Tokens are pieces of text counted by the model service. The gateway quarantines this result instead of treating it as a successful answer.
  9. Finally, the gateway stores the request outcome, token counts, cost, and endpoint in the ledger, and stores the usable response in the cache when appropriate. Recording happens after the result is known so the record can describe what actually occurred.

Local capability-search index over measured model findings

The problem this system addresses

People previously chose a model for an unclear task from memory, while evidence about past model performance was spread across notes and conversation records. This system prevents an old, dead, or poorly supported model from being selected simply because someone remembered it or found its name in an unrelated file.

What the system does

This system searches evidence about what models are good at, rather than merely searching for files. It combines ordinary word matching with semantic matching, which means it can find text that has a similar meaning even when it uses different words. It represents text as an embedding, a list of numbers that summarizes meaning, and compares those lists to rank possible matches. It also records when a model is stale, meaning known to be unavailable or replaced, so that search results can warn against using it.

How it works

  1. First, the system gathers four evidence sources: personal notes, session transcripts, verified findings, and the current kie.ai model catalogue. A source is simply the kind of record from which information was taken. Keeping the sources separate helps show where a finding came from.
  2. Next, it divides the source material into 280 smaller chunks. A chunk is a searchable piece of text. Smaller pieces make it easier to connect a specific task to the relevant evidence instead of returning an entire long record.
  3. For each chunk, the system stores ordinary searchable text information for BM25 matching. BM25 is a scoring method that gives higher scores when the important words in a query appear in a relevant chunk, while reducing the importance of words that appear everywhere.
  4. The system also turns each chunk into an embedding with all-MiniLM-L6-v2. An embedding is a list of numbers representing the text's meaning, and this model produces 384 numbers for each chunk. This second method helps find related wording that does not share the exact same terms.
  5. When someone asks which model fits a job, the system compares the request with the indexed chunks using word matching and embedding similarity. It then ranks evidence about model capability rather than returning only matching filenames.
  6. The system checks its stale markers while presenting findings. A stale marker records that a model should not be trusted for routing, along with why it was marked and when. This step matters after retrieval because a strong text match is still unsafe if the matching model is known to be dead.
  7. When the underlying notes or catalogue change, a rebuild command recreates the local index without a network call. Rebuilding after source changes keeps search results aligned with the stored evidence, while avoiding an unnecessary external request.

Browser MCP automation broker with isolated browser sessions

The problem this system addresses

A computer program needed to control a real web browser, but giving an AI every available browser action would make the list of choices too large. The system prevents the AI from choosing the wrong browser action because it uses a small public tool list and checks web elements through the browser's accessibility tree instead of trusting text read from an image.

What the system does

This system is a browser automation broker, meaning a small service that receives simple requests and sends them to a larger browser-control system. The AI sees 4 tools, while the broker can internally select from 44 Playwright actions. Playwright is a library that controls a web browser. The system also keeps 29 browser profiles, where a profile is a separate set of browser settings and stored website data, and uses a pinned Chromium build, which is a fixed browser version, for compatibility. It can run without displaying a browser window, called headless mode, and checks the browser's accessibility tree, which is a structured description of page elements used by assistive technology, before clicking.

Unified scoped event log and vector index across chat clients

The problem this system addresses

Different chat programs stored their records separately, so a decision made in one program was difficult to find in another. The system prevents cross-project results from being mistaken for current-project evidence by attaching a scope label and applying scope filtering in the database.

What the system does

This system stores events, which are records of actions or messages, in one append-only database, meaning new records are added without rewriting old records. It also stores searchable numerical representations called vectors, which allow related text to be found by meaning rather than exact wording. Each record has a scope, meaning a label for the project or system it belongs to. Five tools are available to chat clients, while three maintenance operations are kept in a local command-line program, which is a text-based tool used by an operator.

How it works

  1. First, each client sends an event to the shared event store. An event is a record such as a tool call, decision, or message, and the shared store prevents each client from keeping an isolated history.
  2. Next, the event receives a scope label. A scope identifies the project or broader area that the event belongs to.
  3. The database applies scope filtering before returning results. This order matters because filtering in the database is more dependable than asking a language model to ignore unrelated results after they have already been retrieved.

Five-gate post-render video QA gate with on-screen caption presence and caption-to-script alignment

The problem this system addresses

A rendered video could pass checks on its input files and still contain visible or audible defects in the final file. This system prevents specific shipped failures, including missing or mistimed captions, long silence, missing music, wrong visual content, and repeated frames, by checking the rendered video itself.

What the system does

This system runs five checks on the completed episode directory and refuses the episode if any check fails. It uses audio and video inspection tools, image-pixel checks, caption timing data, and a vision-capable language model, which is a model that can inspect video and return a structured judgment. It also aligns spoken-word timings with the script so captions use the script's spelling while retaining timing information from the transcription. OCR, or optical character recognition, is used only as an advisory measurement and does not decide whether an episode passes.

How it works

  1. The gate first locates the rendered video by trying the expected file name and then any MP4 file in the episode directory. This matters because a directory name and a video file name may differ.
  2. Gate 1 checks audio and duration. It uses ffprobe, a tool that reads media properties, to compare the video duration with the voice duration plus the expected call-to-action card. It allows a 3.0 second difference. It also searches for trailing silence longer than 3.5 seconds and refuses the episode when no music bed is present.
  3. Gate 2 checks the caption timing and text data. It compares captions with nine known phonetic transcription errors and refuses the first matching corruption. It also measures the gap between the last caption word and the end of the voice track and refuses a gap greater than 2.0 seconds.
  4. Gate 3 checks burned-in captions in the actual rendered pixels. It samples at the midpoint of each caption word, looks for bright glyph pixels next to dark outline pixels, checks the expected accent colour, and requires at least 1200 glyph pixels on a qualifying frame. At least 80 percent of narration frames must contain a caption. This comes after the caption-track check because a correct text file does not prove that text was visibly drawn into the video.
  5. Gate 4 sends the actual rendered video to a vision model in groups of 6 shots. The model returns a structured judgment for each shot about the subject, narration beat, and orientation. Missing judgments for any shot cause refusal. The model chain tries minimax-m3 first and gemini-3.1-pro-preview second, with different answer budgets based on observed reasoning failures.
  6. Gate 5 checks for repeated frames. It refuses consecutive duplicate frames, any reused frame, or a repeated block where shots 1 to 16 match shots 17 to 32.
  7. Before Gate 2, the alignment stage compares transcription tokens with script tokens using a sequence matcher. It keeps the transcription timings but replaces transcription spelling with the script spelling. If word counts differ, it distributes the original time span across the script words according to word length, and it saves the original transcription separately.
